- (direction) Feature chosen for BMAD pilot phase 4: generic attribute rules, the first item in architecture.md Deferred; extends FR-7 and AD-2.
- (decision) Operators: 'in' and 'not in' only (user choice); keeps editor and audit wording simple.
- (decision) Missing attribute never matches, for both operators (user choice); mirrors % rollouts skipping users without an ID.
- (decision) Attribute names are free text validated by a safe pattern; no registry table (user choice).
- (decision) Demo users get a country and a seeded flag targets one, shown in the debug panel (user choice).
- (constraint) MCP set_flag_rules has a hand-written JSON schema enumerating rule types (AdminTools ~L279, L339); it must gain the new type.
- (constraint) Seed changes need a new migration V5; V1-V4 are committed and append-only (AD-11).
- (assumption) Values match exactly and case-sensitively, like user and customer IDs.
- (assumption) Value format reuses the rule-ID pattern (letters, digits, _ . : @ -, max 128).
- (assumption) 'customer' is allowed as an attribute name even though a customers rule exists.
- (capability) CAP-1: an editor or admin can target users by an attribute value being in / not in a list; evaluation honours it with missing never matching.
- (capability) CAP-2: the admin rule editor creates and edits attribute rules; the audience sentence and audit summary describe them in plain words.
- (capability) CAP-3: agents create attribute rules through MCP set_flag_rules with the same validation.
- (capability) CAP-4: evaluation results name the rule kind 'attribute' and the storefront debug panel labels it, never exposing names or values.
- (capability) CAP-5: the demo storefront shows an attribute rule working via fictional user countries and a seeded flag.
- (assumption) Attribute name pattern ^[a-z][a-z0-9_]{0,63}$ (lowercase, like JSON keys in demo context).
